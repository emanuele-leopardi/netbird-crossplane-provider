# netbird-crossplane-provider

A [Crossplane](https://crossplane.io/) provider for [NetBird](https://netbird.io).
It lets you declare your NetBird account — groups, policies, setup keys,
networks, network resources, network routers, DNS settings, nameservers, users
and access tokens — as Kubernetes resources and reconcile them against either
NetBird Cloud or a self-hosted NetBird management server.

This repository is a fork of
[`infitx-org/netbird-crossplane-provider`](https://github.com/infitx-org/netbird-crossplane-provider)
that has been ported to **Crossplane v2**. See
[Differences from upstream](#differences-from-upstream) for the full list.

## Requirements

- Crossplane **v2.x** (developed against v2.4.3)
- Kubernetes **v1.30+** (developed against the k8s v0.36 libraries)

This provider is namespaced-only. It does **not** work with Crossplane v1
without modifications.

## Install

```shell
kubectl apply -f examples/install.yaml
```

The provider is published as an xpkg, so you can also install it directly:

```shell
kubectl crossplane install provider ghcr.io/emanuele-leopardi/netbird-crossplane-provider:v1.0.0
```

Wait for the provider to become healthy:

```shell
kubectl get providers.pkg.crossplane.io
kubectl get providerrevisions.pkg.crossplane.io
```

## Configure credentials

Every API this provider serves lives in a single group:
`netbird.m.crossplane.io/v1alpha1`. That group contains both the namespaced
`ProviderConfig` and the cluster-scoped `ClusterProviderConfig`.

Create a NetBird personal access token (`nbp_…`) in the NetBird dashboard under
**Settings → Access tokens**, then either

- apply `examples/namespaced/providerconfig.yaml` to create a namespaced
  `ProviderConfig`, or
- apply `examples/namespaced/clusterproviderconfig.yaml` to create a
  `ClusterProviderConfig`, which can be referenced from any namespace.

Managed resources pick a config with `spec.providerConfigRef`:

```yaml
spec:
  providerConfigRef:
    name: default
    kind: ClusterProviderConfig # optional; defaults to ClusterProviderConfig
```

If you use OAuth2 client credentials instead of a token, set
`credentials-type: oauth` and `oauth-issuer-url` on the config, and store a JSON
document with `client_id`, `client_secret`, `grant_type` and `scope` in the
credentials Secret.

## Managed resources

| Kind | Description |
|------|-------------|
| `NbGroup` | A peer group |
| `NbPolicy` | An access control policy |
| `NbSetupKey` | A reusable or one-off setup key (writes the plaintext key to a connection Secret) |
| `NbNetwork` | A network (site-to-site routing) |
| `NbNetworkResource` | A resource inside a network |
| `NbNetworkRouter` | A routing peer for a network |
| `NbNameServer` | A nameserver group |
| `NbDnsSetting` | Account-wide DNS settings |
| `NbAccessToken` | A personal access token (writes the token to a connection Secret) |
| `NbUser` | A user |
| `NbAccount` | Account settings |

See `examples/namespaced/` for one manifest per kind.

### Connection secrets

`NbSetupKey` and `NbAccessToken` publish their generated secret value under the
`password` key. Because these resources are namespaced, the target Secret must
be in the same namespace:

```yaml
spec:
  writeConnectionSecretToRef:
    name: netbird-setup-key
```

A setup key's secret changes whenever the provider replaces the key, which
happens when the key in NetBird has expired or has been revoked. Revocation is
one-way in the NetBird API, so a revoked key is always replaced with a fresh one
rather than revived.

The secret is rewritten from the key NetBird holds on every reconcile, so it can
also be restored if it is deleted by hand. While a key is being replaced the
secret is briefly empty, because at that moment no key exists.

### Referencing groups

Peers registered with a setup key are placed in the groups named by
`spec.forProvider.auto_groups`. Rather than hard-coding NetBird group IDs, which
are generated by NetBird, you can reference `NbGroup` resources:

```yaml
spec:
  forProvider:
    auto_groups_refs:
      - name: htpc
      - name: servers
```

or select them by label:

```yaml
spec:
  forProvider:
    auto_groups_selector:
      matchLabels:
        netbird.example.com/managed: "true"
```

Crossplane resolves these references before the setup key is reconciled, reading
each group's NetBird ID from its `crossplane.io/external-name` annotation. A
group that has not been reconciled yet therefore blocks the setup key with a
"cannot resolve references" event until the group exists, which is what orders
group creation ahead of the key that uses it.

`auto_groups` accepts raw NetBird group IDs and is normally left empty; if it is
set, it takes precedence over the references and is never overwritten.

`NbPolicy`'s rule `sources` and `destinations` take `{name: ...}` or `{id: ...}`
entries instead, and resolve the group by name against the NetBird API. A rule
written with names is compared against NetBird's groups by name, so it does not
look like drift just because the API also reports an ID, and a reference that
resolves to nothing fails the reconcile instead of silently producing a rule
over no groups.

## Differences from upstream

- **Full Crossplane v2 port.** `crossplane-runtime/v2`, `crossplane/apis/v2`,
  controller-runtime `v0.24`, Kubernetes `v0.36`.
- **Namespaced API only.** Upstream served cluster-scoped managed resources from
  `vpn.netbird.crossplane.io` and `netbird.crossplane.io`. Both are replaced by a
  single, namespaced group, `netbird.m.crossplane.io`, in the style of
  `provider-terraform`'s `tf.m.upbound.io`. Cluster-scoped managed resources are
  not (yet) served; the namespaced tree can be copied to re-add them.
- **`ClusterProviderConfig` support.** A namespaced managed resource may
  reference either a namespaced `ProviderConfig` or a `ClusterProviderConfig`.
- **CRD gating (`SafeStart`).** Controllers only start once their CRDs are
  established, so a provider that is installed before its CRDs does not hot-loop.
- **External Secret Stores support removed.** `StoreConfig` and the
  `EnableAlphaExternalSecretStores` plumbing are gone; that API is not part of
  Crossplane v2.
- **`Disconnect` implemented.** The v2 external-client interface requires it.
- **`NbSetupKey` reconciles drift.** `Observe` used to hard-code
  `ResourceUpToDate: true`, so editing `auto_groups` did nothing. It now
  compares the resolved groups against NetBird's, and `Update` corrects them
  through `PUT /api/setup-keys/{id}`, which is the only field NetBird lets you
  change on an existing key.
- **`NbSetupKey` no longer replaces a key that never expires.** The old expiry
  check was `Expires.Before(time.Now())`, but NetBird returns the zero time for
  a key created with `expires_in: 0`, so every non-expiring key looked expired
  and was deleted and recreated on every reconcile. The replacement decision now
  uses the state NetBird reports (`expired` or `revoked`).
- **`NbSetupKey.auto_groups_refs` / `auto_groups_selector` added**, so a setup
  key can reference `NbGroup` resources instead of hard-coding generated IDs.
- **`NbSetupKey.spec.forProvider.revoked` removed.** Revocation is one-way in
  the NetBird API and a new key is never created revoked, so no desired value of
  that field could ever be satisfied. `revoked` remains in `status.atProvider`.
  To revoke a key, revoke it in NetBird and let the provider replace it, or
  delete the resource.
- **A key's connection secret is no longer blanked.** The managed reconciler
  republishes whatever `Observe` returns, and it writes whenever the data
  differs from what is already in the Secret. `Observe` returned no details, so
  every reconcile of an up-to-date `NbSetupKey` erased the key from the Secret
  its consumer reads, and the consumer then failed with `couldn't find key
  password`. `Observe` and the in-place `Update` now publish the key.
- **Groups are resolved by one shared, safe helper.** The old resolver reported
  an error only when *no* entry resolved, so a partially resolvable rule
  silently produced an empty group ID, and it panicked on an omitted list, which
  is how a rule's `sources` and `destinations` are declared. The controller
  package was also renamed from `auth` to `nb`, since it holds more than
  authentication, and `NbNetworkResource` no longer dereferences
  `groups[].name` unconditionally.
- Deleted the template leftovers: `examples/composite`, `examples/storeconfig`,
  `examples/curltest.sh` (which contained a hard-coded API token).
- The NetBird Go SDK is still pinned to the version upstream used
  (`v0.50.1`). Bumping it is a separate change, since the NetBird REST API
  structs moved between releases.

## Developing

Code generation uses the `generate` build tag and drives `controller-gen` and
`angryjet` directly, so it does not need the `build` submodule:

```shell
cd apis && go generate -tags generate ./...
```

That regenerates `apis/namespaced/v1alpha1/zz_generated.*.go` and
`package/crds/*.yaml`.

Common targets (these use the `build` submodule; run `make submodules` first):

```shell
make generate     # run the above plus go mod tidy
make check-diff   # fail if generated files are stale
make reviewable   # generate + lint + test
make test         # unit tests
make build        # build the linux binaries into _output/bin
make build.all    # build the binaries and the container images
```

### Building and publishing the package

A Crossplane package is two artifacts: a distroless controller image holding
just the provider binary, and the package image that carries the CRDs and
`package.yaml` and points at that controller. `make publish` handles both.

`make publish` refuses to run on a dirty tree and stamps the version from
`git describe`, so tag the commit you are publishing first:

```shell
docker login ghcr.io
git tag v1.0.0
make build.all
make publish
```

`XPKG_REG_ORGS` already points at `ghcr.io/emanuele-leopardi`, and the branch is
`main`, which is one of the branches the build system publishes from. The result
is `ghcr.io/emanuele-leopardi/netbird-crossplane-provider:v1.0.0`, which is what
the Crossplane `Provider` in `home-clusters` pulls.

The controller image is pushed by the package machinery, not by the image
targets, so a plain `docker push` of the image the build leaves in the daemon is
neither needed nor sufficient.

If you would rather not use the `up`-based build, build the two artifacts by
hand:

```shell
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o _output/bin/linux_amd64/provider ./cmd/provider
crossplane xpkg build --package-root=package --examples-root=examples \
  --controller=ghcr.io/emanuele-leopardi/netbird-crossplane-provider:v1.0.0 \
  -o netbird-crossplane-provider.xpkg
crossplane xpkg push -f netbird-crossplane-provider.xpkg \
  ghcr.io/emanuele-leopardi/netbird-crossplane-provider:v1.0.0
```
